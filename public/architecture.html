System walkthrough

How DoodleDisaster works

A realtime multiplayer drawing game with no game server, no accounts and no bill — running entirely on a free Vercel project and a free Supabase project. Here is how the pieces fit, and which trade-offs paid for that.

The shape of it

Three tiers, and the interesting decision is what doesn't go through the middle one. Pick a flow to trace it through the system — the diagram highlights the path, and you can step through it beat by beat.

Why there is no game server

The whole design falls out of one constraint: a free Vercel project gives you stateless functions that live for the length of a request. No sockets you own, no timers, no memory between calls. Three consequences:

Strokes never touch the server

Ink goes browser → Supabase Realtime → browser. Points are quantised into a 1000×750 virtual space, batched every 100ms, and applied on the far side with quadratic smoothing.

Trade-off: nothing to replay for a late joiner — so a newcomer broadcasts sync_req and the drawer answers with the full op-list.

State is one row, guarded by a version

Every mutation is load → mutate → save WHERE version = n, retried up to four times. Two people guessing the same word in the same millisecond can't both win the points.

Trade-off: a write round-trip per action, so the UI updates optimistically and lets the authoritative state confirm.

Time is a client conspiracy

Nothing on the server wakes up when a turn ends. Every client watches the clock and races to POST advance, staggered by their index so they don't stampede. The first one wins the version check; the rest no-op.

Belt and braces: a GET also heals a stuck room, and abandoned games are closed out opportunistically on room creation.

The word is never sent to a guesser

sanitize() builds a per-player view: the mask, who has solved it, your own hint count. The answer is only ever attached to the drawer's copy.

Consequence: guessing has to be a server call — the client physically cannot check the answer itself.

Party mode: keeping a secret on a mirrored screen

Casting to a TV means there is no private surface. The fix is topological rather than visual — the word travels on channels the wrong devices are not subscribed to.

ChannelSubscribersCarries
party:CODEscreen + every phoneroster, teams, scores, clock, commands. Never a word.
party:CODE:tNteam N's phones onlythe word that team is choosing

The screen subscribes to no team channel, so it cannot receive a word early even by accident — it learns it exactly once, in the reveal command, at the moment it is meant to go up on the telly. A phone subscribes only to its own team's channel and re-subscribes if the host moves it.

Why the screen owns the game. Any number of phones can drive a party game, so every mutation is serialised on the one device guaranteed to be present and awake. Two people tapping “they got it” at the same instant still only scores once, because the second command arrives to find the phase already moved on.

Never dealing the same word twice

The original bug: every new room started its deck at position zero, so a second game with the same friends dealt identical words. Not bad luck — a guaranteed repeat.

Each tier is shuffled once into a fixed ring using a per-group seed, and a cursor walks it forward. A word cannot come round again until every other word in that tier has been dealt. The cursor is carried between games on the players' own devices and adopted from whichever room they join, so a group keeps walking one long ring all night.

Questions you'd probably ask

Why Supabase Realtime rather than raw WebSockets?
Vercel functions can't hold a socket open on the free tier, so something else has to own the connection. Supabase Realtime is a hosted Phoenix channel server: browsers connect directly to it, the app never proxies ink, and the server can still push into a room by POSTing to the broadcast endpoint. The alternative — a long-lived Node process — means a bill and a thing to babysit.
What happens when the drawer closes their laptop mid-turn?
Their leave marks them disconnected; if they were drawing, the turn resolves. Host duties migrate to the next connected human, and the room remembers its founder so the crown returns when they come back. If everyone drops, the game pauses rather than ending — it sits in a holding state with an “end the game” button for the host, because a dropped signal shouldn't destroy a night.
How do bots draw without a server?
The host's browser drives them. Each bot word maps to a hand-authored recipe in a 100×75 grid, then a humaniser adds tremor, minimum-jerk velocity, hesitation and the occasional “oops” stroke followed by an undo — fitted to about two thirds of the draw timer. It replays through exactly the same broadcast path a person's hand would use, so no other client can tell the difference.
Where do the drawings go?
At the end of each turn the canvas is downscaled to a small jpeg and stored in doodle_shots, keyed by room and turn, so everyone sees the same end-of-night gallery including people who joined late. Each device also keeps its own copy so old games open instantly and work offline.
What does this cost to run?
Nothing. A handful of daily players fit inside the Vercel hobby tier and the Supabase free tier with room to spare — the entire database is a few megabytes, most of it jpegs. The design constraints on this page are almost all downstream of choosing to stay inside those limits.
